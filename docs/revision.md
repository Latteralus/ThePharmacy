# TypeScript Migration Plan (incremental, in-place)

> **Status: active, living document.** This describes how the codebase is
> moving from plain JavaScript to TypeScript. Update the "Progress" section
> below whenever a file converts. See `docs/Changelog.md` for the narrative
> session-by-session log of *why* changes happened; this file is the
> current state of the migration itself.

## Why not a full rewrite

An earlier version of this document (through 2026-08-15) planned a ground-up
rewrite onto Webpack + React + Redux + TypeScript — new build pipeline, new
UI framework, new state management, all at once. It was never built.

That direction was deliberately dropped, not just left unfinished. This
project has already been burned by exactly the failure mode a rewrite
invites: the "TestTime" commit (see `docs/Changelog.md`'s Glossary) made a
large simultaneous architecture change — deleted a data file, gutted several
modules, switched one file to ES-module syntax mid-`<script>`-tag codebase —
and the breakage went unnoticed for almost a year, because nothing about the
change could be verified incrementally. A React/Redux/Webpack rewrite is the
same shape of risk at a much larger scale: an extended period where the
"new" version and the "real" version diverge, with no way to confirm parity
until the whole thing is done.

TypeScript itself doesn't require a bundler or a UI framework — those are
separate, later decisions. The plan here gets type safety onto the existing,
working architecture with no behavioral change at each step.

## Approach

- **No bundler, no module system change.** The app stays exactly what it is
  today: `main.html` loads plain `<script>` tags in a fixed order; modules
  communicate through `window.*` globals. `tsc` compiles `.ts` → `.js` in
  place (`module: "none"`, no `outDir`), so every `<script src="...">` tag,
  and every `test/unit/*.test.js`'s `require('../../main/js/...')` call,
  keeps pointing at the same path and keeps working unchanged.
- **Compiled `.js` is a build artifact, not source, for any file that has
  converted.** Once `foo.js` becomes `foo.ts`, the generated `foo.js` is
  gitignored and regenerated by `npm run build:ts`, which is chained in
  front of every script that needs fresh code (`start`, `test`, `test:e2e`,
  `dist`, `publish`). A checked-in `.js` that silently drifts from its `.ts`
  source is exactly the kind of staleness bug this project has repeatedly
  hit (see the Changelog's Cashier-wage and stale-role-string bugs) — one
  source of truth avoids the whole category.
- **`strict: true` from the start.** Retrofitting strict mode onto a
  growing TS codebase is much more painful than starting with it.
- **Ambient `window` typings accumulate in `main/js/types/global.d.ts`**,
  gaining one small interface per converted file. Files not yet converted
  are simply untyped globals as far as TS is concerned — no upfront effort
  to type the whole `window` surface at once.
- **Conversion order: leaf-most files first.** A file that only *assigns*
  `window.*` globals (no reads of others) converts with zero new ambient
  dependencies. Files with heavier cross-module reads (most of
  `main/js/data/*.js`, and effectively everything in `main/js/pages/`)
  convert later, once enough of what they depend on already has types.
- **One file (or a very small, related batch) at a time, each independently
  verified**: `npm run build:ts` compiles clean → `npm test` passes →
  `npm run test:e2e` passes → the real app launches and the affected feature
  is checked by hand. No multi-file batch conversions without a passing
  checkpoint in between.

## Naming conventions (for when files convert)

Kept from the original plan, since they're sound regardless of rewrite vs.
incremental — apply them to any `.ts` file/interface/type as it's created,
not retroactively to everything at once:

- **File names**: keep existing names, just swap the extension
  (`insurance.js` → `insurance.ts`) — no renaming to kebab-case mid-migration,
  that's a separate, larger change.
- **Interface names**: PascalCase, no `I` prefix (`InsurancePlan`, not
  `IInsurancePlan`) — matches modern TS convention rather than the
  C#-influenced style the original plan used.
- **Type names**: PascalCase (`EmployeeRole`, not `TEmployeeRole`).
- **Everything else** (functions, variables, constants): unchanged from
  whatever the existing `.js` file already used — this migration is about
  adding types, not a style rewrite.

## Later, separate decisions (explicitly out of scope for now)

These may be worth revisiting once most of the codebase has types and the
migration itself is old news — not before:

- A bundler (Vite/esbuild/Webpack), if the `window`-global pattern ever
  becomes the actual bottleneck rather than a mild inconvenience.
- A UI framework (React or otherwise), if `main/js/pages/*.js`'s
  string-concatenation-based rendering becomes hard to maintain.
- State management (Redux or otherwise), same condition as above.

None of these are needed to get type safety, and bundling them into "the TS
migration" is exactly the scope creep that turned the original plan into a
16-week rewrite that never shipped.
